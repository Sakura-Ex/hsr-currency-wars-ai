# 文档写作规范

## 写作原则

- 面向读者的实际任务组织内容，让读者能找到信息、完成操作并判断结果。
- 保持准确、清楚、直接。用具体动作、对象和结果说明问题。
- 命令、路径、配置和示例与当前项目保持一致。
- 说明必要的前提、限制和重要设计决定。
- 不重复维护同一内容；相关文档通过链接关联。

## 语言风格

- 面向公众的项目介绍、玩家指南和发布说明提供英语与简体中文两个版本，并设置语言切换入口。
- 双语版本同步维护功能状态、内容结构、参数、命令和链接。根目录以 `README.md` 提供英文入口，以 `README.zh-CN.md` 提供简体中文入口，两者互相链接。
- 设计文档、开发约定、任务安排和项目协作使用中文。
- 代码标识符、路径及工具固定字段保留原名。
- 使用简洁、自然、具体的表达，一句话尽量只讲一个重点。
- 优先正向陈述，直接说明是什么、怎么做、会得到什么结果。
- 少用抽象词、空话、套话和不必要的术语。
- 使用自然易懂的表达，避免生硬的名词组合。
- 术语前后一致；读者可能不熟悉的术语首次出现时作简要解释。
- 操作步骤明确写出动作和预期结果。

## 文档组织

文档按项目总览、游戏数值、开发约定和模块资料组织：

| 位置 | 职责 |
| --- | --- |
| `docs/README.md` | 项目文档总入口，指向各类文档入口 |
| `docs/project/` | 项目目标、整体设计、实施计划和共用规则 |
| `docs/game-data/` | 跨模块共用的游戏数值、ID 对照及计算口径 |
| `docs/development/` | 跨模块适用的开发、协作、目录和写作约定 |
| `docs/modules/README.md` | 模块目录，每个模块维护一条入口和当前能力说明 |
| `docs/modules/<模块>/README.md` | 模块总览，说明用途、范围、实现状态和推荐阅读顺序 |
| `docs/modules/<模块>/` 的其他页面 | 该模块的设计、参数、接口、使用方法和验证说明 |

每个目录的 `README.md` 帮助读者选择下一步阅读内容。模块增加详细页面时，在模块自己的入口登记；新增模块或上层入口变化时，再更新对应上层索引。

同一模块的内容按读者任务拆分。例如设计说明解释职责与调用关系，参数页说明输入和取值，使用页提供运行方式，验证页说明检查方法和结论。根据实际内容增长增加页面，入口突出当前可用能力和关键步骤。

跨模块规则在对应共用文档维护，游戏数值与 ID 对照集中在 `docs/game-data/`，模块页面通过链接引用。页面使用相对链接，移动或拆分后同步更新引用。长页面按主题组织章节，操作步骤使用有顺序的列表。

根目录 `README.md` 面向初次访问者，介绍项目用途、主要目标、当前状态和使用入口，并保留许可证信息。语言、目录和协作等维护约定集中在开发文档中，通过文档入口查阅。`AGENTS.md` 记录代码助手的操作约定；`CONTRIBUTING.md` 提供贡献入口，并链接开发约定。发布时用 `CHANGELOG.md` 记录用户能感知的变化。

## 文档维护

- 新增或拆分页面时，更新所属目录的阅读入口；上层入口变化时同步更新对应索引。
- 功能、配置或流程变化时，同步更新相关文档。
- 删除功能时删除相关说明，更换方案时更新正文和链接。
- 在正文中区分规划、已实现的行为和实测结果。
- 变更过程及原因保存在 Git、Issue 和 PR 中。
- 修正过时内容，保持各文档之间一致。
- 让读者能够根据说明完成目标，并判断操作是否成功。

## AI 写作注意事项

- 正面说明要求或结果，避免补充无必要的否定或免责说明。
- 不在文档中说明内容来源。
- 新增规则的篇幅和语气应与已有规则一致。
