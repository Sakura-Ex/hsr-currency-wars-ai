# Git 协作规范

每个 PR（拉取请求）包含一项完整改动。随着代码量和参与人数增加，调整协作流程。

## 主分支保护

主分支 `main` 已启用 [GitHub 保护规则](https://github.com/Sakura-Ex/hsr-currency-wars-ai/rules/26374665)。所有改动在独立分支提交，通过 PR 合并到 `main`；至少获得一位评审批准，并通过相关检查后，使用 squash merge 合并。

## 开发前同步

开始或恢复开发时，先检查当前分支和工作区，确认以下三项：

| 对象 | 用途与示例 |
| --- | --- |
| PR 目标分支 | 本次改动要合入的分支，如同仓库的 `origin/main`，或 fork 场景的 `upstream/main` |
| 任务分支的上游 | 该任务分支的远端副本，通常为 `origin/codex/<主题>`，供 `git pull` 同步协作者的提交 |
| 推送远端 | 发布任务分支的仓库，同仓库和 fork 场景都可能使用 `origin` |

按以下顺序同步：

1. 妥善保存已有未提交改动，其他任务的内容单独保留。当前任务分支已有上游时，确认其指向远端任务分支，再执行 `git pull --ff-only`；尚无上游时跳过 pull。
2. 每次均抓取 PR 目标分支：执行 `git fetch <目标远端> refs/heads/<目标分支>:refs/remotes/<目标远端>/<目标分支>`，明确更新 `<目标远端>/<目标分支>`，包括抓取配置仅覆盖部分分支的情况。
3. 新任务从该目标分支创建：`git switch --no-track -c codex/<主题> <目标远端>/<目标分支>`。已有任务则在任务分支执行 `git merge --ff <目标远端>/<目标分支>`：已包含目标历史时保持不变，可快进时快进，已分叉时创建合并提交。解决冲突后完成相关验证。

命令失败、历史关系异常或冲突尚未解决时，先处理原因，再继续开发。任务分支的同步合并保留已发布历史；合入受保护的 `main` 时使用 PR 的 squash merge。

首次发布任务分支时，执行 `git push -u <推送远端> <任务分支>`，将上游设置为远端同名任务分支。后续同步分别核对任务上游和 PR 目标分支。推送前再次抓取 PR 目标；目标更新时先同步，再重新验证和独立评审。

Git 官方命令手册：[pull](https://git-scm.com/docs/git-pull)、[fetch](https://git-scm.com/docs/git-fetch)、[switch](https://git-scm.com/docs/git-switch)、[merge](https://git-scm.com/docs/git-merge)。

## 任务与评审流程

每个任务写明目标、输入输出、验收条件和负责人。划分任务时，确保每项任务都能独立演示和评审。

按以下流程协作：

1. 领取任务，确认负责人和验收条件。
2. 创建短期分支，实现改动并完成相关验证。耗时较长的任务可提前建立草稿 PR，让同伴了解接口和进度。
3. 代码助手先完成下述独立评审，再提交 PR，说明结果、主要改动和验证证据。
4. 请同伴评审；涉及共享接口时，请接口使用方参与。
5. 处理评审意见，有重要变化时再次请求评审。至少获得一位评审批准，并通过相关检查后合并。

## PR 前独立评审

代码助手创建 PR 或向已有 PR 推送新改动前，必须启动不继承当前对话历史的独立子 agent 评审本次改动。

1. 向评审者提供任务要求、仓库位置、PR 目标分支和待评审的提交范围。评审以实际准备推送的 Git 提交为准。工作区中其他未提交内容按任务范围单独保留。
2. 评审者自行阅读仓库规范、相关实现、测试和文档，对照验收条件核对完整差异。沿实际调用链查看受影响的入口、调用方和数据，明确改动后需要继续成立的规则和既有行为。
3. 主动构造可能破坏这些规则或行为的反例。根据改动选取边界条件、失败路径和既有用法，优先用最小复现、旧版对照或小规模穷举验证。
4. 每项发现写明位置、触发条件、预期结果、实际或可推导的结果，以及影响和严重程度。评审结论写明实际检查的场景、验证结果和待核实事项。
5. 主 agent 在轮次上限内逐项核实并修正成立的问题，记录未采纳意见的原因。修正后按原触发条件复验。复审聚焦上一轮之后的差异及其影响，同一问题更新原记录。任务记录保留轮次、目标分支、提交版本、结论和处理结果，确保评审结论对应最终待推送的提交。
6. 同一项改动的自动独立评审最多 3 轮，包含首次评审和最多 2 轮复审。更换评审者、重开会话或提交修正时沿用原计数。第 3 轮结束后仍有待解决的问题时，主 agent 停止自动修正和复审，保留当前提交，向用户报告未解决的问题、验证结果和建议的下一步，由用户决定如何继续。

## PR 内容与合并要求

PR 正文使用以下结构：

```markdown
## 目标与结果
说明具体场景和实现后的行为，关联任务。

## 主要改动
说明评审需要关注的模块、规则或接口变化。

## 验证
列出实际执行的命令、使用的样本和结果，说明验证覆盖的范围。
```

评审时检查需求是否满足、规则是否正确、代码是否易读、验证是否充分，以及文档是否与改动一致。

通过 PR 向主分支合并改动，使用 squash merge 将一个 PR 中的提交合并为一次提交。新增必需检查时，其名称应与仓库中实际运行的检查任务一致。

## 分支命名

手动创建的分支建议命名为 `feat/<主题>`、`fix/<主题>`、`docs/<主题>`。Codex 创建的分支使用 `codex/<主题>`。

## 提交粒度与时机

每个提交包含一项可独立说明、验证和撤销的完整改动，按以下标准拆分：

- 同一功能的实现、相关测试和必要文档一起提交。
- 无关功能、独立修复和大范围格式调整分别提交。
- 较大任务按可通过相关检查的阶段拆分提交，每个阶段有明确结果。
- 每完成一项完整改动并通过相关验证后及时提交。
- 提交前核对差异和暂存内容，确保提交内容属于本次改动，保留工作区中其他任务的改动。

## 提交信息

提交信息使用英文，标题采用以下格式：

```text
type(scope): description

feat(sim): add crystal settlement for reward nodes
fix(battle): apply freeze removal in the observed order
docs(plan): clarify acceptance criteria for initial battle samples
test(replay): add a case for reproduced positioning differences
refactor(state): consolidate resource update logic
ci(checks): add battle module tests
```

type 表示改动类型，使用 `feat`、`fix`、`docs`、`test`、`refactor`、`perf`、`build`、`ci`、`chore`；scope 表示涉及的模块，使用实际模块名称。正文按需补充改动原因、行为变化和关联任务。

PR 标题同样使用英文和上述格式，合并后用作主分支上的提交标题。
