# 开发与测试约定

状态：讨论稿。日期：2026-11-05。

## 质量要求

每项改动都应说清楚：解决什么需求、实现后如何运行、如何验证已经完成。

明确各模块的职责，确保测试结果可复现、文档与实际行为一致。

## 代码约定

按职责组织模块，接口字段根据当前使用场景确定。集中维护各模块共用的游戏规则，策略通过环境提供的观测获取信息，通过动作与环境交互。

函数和类型的名称应说明具体用途；注释解释规则依据、执行顺序或这样实现的原因。使用所选语言的标准工具格式化代码，通过相应锁文件固定依赖版本。

模拟中的随机过程应使用显式传入的种子或随机源。记录状态时，区分环境的完整状态和策略能看到的观测信息，确保研究评估使用的信息与实际运行时一致。

出现重复实现，或当前需求明确需要共用代码时，将这些代码提取为共用函数或模块。根据测量结果优化性能，根据关联任务和验收条件确定每次改动的范围。

完成功能时，一并完成正常规则和核心状态变化的测试。项目发起人在实际测试中发现边界情况的差异后，先确认能够复现，再按以下步骤处理：

1. 记录实际输入与结果。
2. 确认预期规则。
3. 增加回归用例。
4. 修正对应实现。

## 默认禁用的掩盖问题写法

下表以 TypeScript、JavaScript 和 Python 举例，其他语言中的同类做法按相同原则审查。

按实际用途审查下表中的写法。修复时优先检查规则由谁维护、输入输出的类型是否对应，以及数据如何传递。

| 写法 | 默认禁止的用途 | 优先处理方式 |
| --- | --- | --- |
| 非空和确定赋值断言 `value!`、`field!:` | 用断言宣称值一定存在或字段已经初始化，代码本身却缺少相应保证 | 直接传递已取得的值或遍历元素；通过显式初始化、判别联合明确值何时可用。外部数据可能缺失时，在入口处理 |
| `any`、`as any`、`as unknown as T`、`as never`、Python `cast` | 绕过类型错误，将非法值当作合法值使用 | 外部数据先用 `unknown` 接收并验证；内部代码修正类型和接口。破坏性测试通过原始存储或输入接口注入非法数据 |
| 类型断言 `as T`、类型谓词、断言函数 | 未经验证就宣称数据符合某种结构，或把这类断言藏进通用辅助函数 | 优先使用类型推导或 `satisfies`。类型谓词和断言函数须实际检查其声明的条件 |
| `@ts-ignore`、`@ts-expect-error`、`eslint-disable`、`type: ignore`、`noqa` | 屏蔽尚未解决的报错或警告，关闭整个文件的检查，或整体禁用某条规则 | 修复报错根因，或修正工具使用的类型信息。编译期反例测试、第三方类型缺陷可使用有具体依据且范围最小的例外 |
| 空 `catch`、`catch(() => {})`、失败后返回 `[]`、`0` 或成功状态 | 忽略错误，或把失败当作有效结果返回 | 在负责处理失败的模块处理错误，保留错误发生时的上下文。可恢复的降级行为须有明确的产品约定，并能通过状态、日志或界面识别 |
| `?.`、`??`、`\|\|`、`String`/`Number`/`Boolean` 强制转换 | 用默认值或强制转换掩盖必需数据的缺失、非法输入或类型设计问题 | 先区分业务允许的缺省和数据错误。保留有业务含义的默认值，禁止把错误静默转为零或空字符串 |
| 未处理的 Promise、`void asyncCall()`、用 `async` 或延时消除警告 | 让调用方无法确认任务是否完成或失败；用固定延时、反复清空微任务队列替代实际同步条件 | 明确谁用 `await` 等待结果、谁处理错误，以及何时取消任务。等待实际的完成状态或事件；后台任务也须处理错误 |
| 重复校验、通用 `ensure`/`safe` 包装器、重复维护的状态、临时特殊分支 | 在多层反复检查同一条件，或为缺少实际需求的场景增加状态同步、额外接口或封装 | 每项规则和状态由一个模块负责，其他模块复用已有结果。实现越来越复杂时，重新选择实现方式 |
| 测试中的 `as any` 大对象、替代核心规则的 mock、用被测实现计算期望值、宽泛的 `toThrow` | 用测试替身、绕过类型检查或遗漏关键结果的断言，让有问题的代码通过测试 | 使用最小的合法测试数据，独立确定期望结果。通过实际输入或存储接口测试异常数据，核对具体失败原因，区分业务拒绝、测试环境错误和对象构造错误 |
| 降低检查阈值、扩大 `ignore`/`exclude`、重录快照、扩充基线、跳过失败测试 | 让检查显示正常，却保留代码行为或检查本身的问题 | 保留真实的检查结果，修复导致失败的原因。依据独立于当前实现的行为约定更新快照和基线，逐项核对差异，只接受符合约定的变化 |

### 例外要求

例外必须说明适用范围、始终成立的条件，以及证明这些条件成立的依据。优先在所属接口或必要的局部注释中说明，避免逐行重复。临时绕过工具缺陷时，写明何时撤销该例外。

允许使用 `as const`、`satisfies`、类型测试中的预期编译错误、合法可选字段和有明确含义的默认值。

修复非空断言时，通过初始化、类型定义和传值方式保证所需条件成立。禁止为消除 `!` 而机械添加条件判断和抛错、辅助函数、双重断言或默认值。

## 测试与持续集成

| 改动类型 | 验证重点 |
| --- | --- |
| 规则或公式 | 根据明确规则或实测结果确定输入和预期结果，并核对实现 |
| 战斗和节点流程 | 固定随机种子，检查状态变化和事件顺序 |
| 修复已复现的差异 | 使用原始失败案例，检查修复后的回归测试结果 |
| 搜索与策略 | 在同一组评估场景中比较新策略和参照策略，记录耗时和结果分布 |
| 桌面功能 | Windows 上的实际操作流程 |
| 文档 | 内容一致性、链接、命令及状态描述 |

随着代码增加，在持续集成（CI）中加入格式检查、静态检查和相关测试，优先确保代码能在目标 Windows 环境中运行。在对应的研究任务中运行耗时较长的实验，保存配置和结果。发布时，补充验证在干净环境中的安装过程，以及使用 CPU 运行的流程。

改动完成时，应满足验收条件、通过相关验证、同步更新相关功能文档，并处理完评审意见。验证报告写明实际执行的检查及其结果。

代码评审和合并流程见[Git 协作规范](git-workflow.md)，文档更新见[文档写作规范](documentation-guidelines.md)。
