# 系统设计与技术方案

状态：讨论稿。日期：2026-11-10。账号生成、模拟和模型训练均待实现。

本章按模块职责、架构与模块交互、建议生成流程、技术选型和策略评估的顺序展开。以下架构是供团队与 AI 开发时讨论和细化的方案，具体接口与技术选型通过原型验证后确定。开发顺序见[实施阶段与任务拆解](implementation-plan.md)。

## 模块职责

系统围绕完整对局搭建。运营决策与战斗规划共用对局状态、游戏规则和评估记录，以[项目目标与使用方式](project-overview.md)中的整局通关目标评价方案。

| 模块 | 主要职责 | 输出 |
| --- | --- | --- |
| 战斗引擎 | 按游戏规则计算伤害、行动顺序、技能、状态及事件触发 | 模拟战斗结果与事件记录 |
| 整局环境 | 推进节点，处理商店、投资、经济和生命结算 | 更新后的对局状态、当前可见信息和合法操作 |
| 战斗规划器 | 比较操作序列、站位、自动战斗方案及重试时机 | 战斗建议及其预期收益和耗时 |
| 运营决策器 | 比较购买、升级、储蓄、投资、阵容过渡及转型方案 | 当前节点的运营建议 |
| 阵容研究器 | 探索角色、装备和羁绊之间的配合 | 候选阵容及适用条件 |
| 账号生成器 | 按资源指标和采样条件生成角色、光锥及遗器配置 | 可复现的原始账号配置、生成参数和资源指标 |
| 账号适配器与配置转换 | 接入不同来源，统一字段和单位，按游戏规则转换配置 | 实际生效配置、可用资源及缺失项 |
| 实验评估器 | 回放对局、比较策略，记录模拟与实测的差异 | 包含复现条件、结果和耗时的实验报告 |
| 玩家应用 | 接收账号资源和当前局面，展示建议并记录玩家反馈的结果 | 玩家可在 Windows 本地完成的使用流程 |

## 架构与模块交互

### 调用入口与连接方式

系统按玩家应用、模拟与决策核心、研究与评估工具组织。模拟与决策核心包含账号适配器、整局环境、战斗引擎、运营决策器和战斗规划器；阵容研究器和实验评估器在研究端调用同一套核心接口。共用的规则计算集中在核心中维护。

核心向玩家应用提供统一的建议入口，负责接收请求、检查输入、分配计算预算、选择策略模块并汇总结果。这是核心内部的协调职责，初期可实现为一组本地接口。界面通过该入口获取建议，将玩家确认的实际操作和结果交给核心更新记录。

核心内部优先使用函数或库接口传递结构化数据。玩家应用与研究工具通过本地适配层接入核心；跨语言调用采用语言绑定还是本地进程通信，由原型验证确定。两种方式遵循相同的输入输出约定，保证更换连接方式时模块含义保持一致。

### 共用数据与状态管理

账号导出、程序生成和试用数据先转换为统一的原始账号配置，再由配置转换应用对应版本的游戏数据和强制映射规则，得到实际生效配置与可用资源。模型输入编码和战斗输入组装使用同一份结果；阵容选择和装备分配由策略负责。原始字段、遗器生成、资源评价及首个样例见[账号与遗器数据](account-data.md)。

整局环境结合账号资源、游戏规则版本和当前观测，维护带版本号的对局状态快照；快照表示某个时刻已记录的局面。策略模块读取快照对应的观测并提出候选动作，状态推进与资源结算由整局环境执行。

环境提供给策略的观测包含当前可见信息、合法动作及已知约束。未知信息明确标记为未知；模拟需要补全时，按显式记录的假设或采样生成候选情形。模拟内部的隐藏状态和未来随机结果只用于环境计算与回放，策略输入保留与玩家当时相同的信息范围。具体机制见[游戏规则](game-rules.md)。

每个候选动作都在独立的状态副本上试算，保留动作前后的状态版本和模拟记录。玩家当前局面依据实际观测和反馈更新；更新后生成新版本，并重新检查旧建议是否仍适用。模拟中预测的收益留在模拟记录中，实际资源以玩家确认的结果为准。同一实际操作或结算用事件标识识别，重复反馈只记入一次。

跨模块请求至少关联请求标识、对局标识、状态版本、规则版本、账号配置版本和计算预算。候选动作还需表示候选标识、操作对象、参数及前提条件。返回结果带回来源标识与版本，并说明完成状态、计算耗时和结果依据；发生状态推进时，另注明结果状态的版本。字段的具体类型与序列化格式，在首个可运行样例中共同确定。

### 运营决策与战斗规划的配合

运营决策器从环境提供的合法动作中生成购买、升级、储蓄或调整阵容等候选方案，交给整局环境在副本上推进。需要判断某个方案对战斗的影响时，运营决策器调用战斗规划器，并传入该方案对应的观测、可用配置及剩余计算预算。战斗规划器返回比较结果，由运营决策器结合经济、后续节点和整局目标选择建议。

战斗规划器生成站位、技能操作、自动战斗或重试方案，通过整局环境的战斗评估接口进行试算。环境检查阶段与操作是否合法，准备战斗输入，再调用战斗引擎。引擎负责推进战斗状态，返回当前战斗状态、事件记录，以及战斗结束时的结果和原因。环境根据阶段与规则判断是否进入结算，再将结果交回规划器；中途停止和结算前重试保留各自的状态，节点收益只在满足结算条件时记入一次。战斗引擎专注战斗规则，金币、节点收益和整局进度由环境统一结算。

调用方向保持清楚：运营决策可以请求战斗评估，战斗规划在给定配置和约束内完成搜索；需要比较换阵容或购买方案时，将评估结果返回运营决策器继续处理。这样，同一候选方案的战斗计算与运营比较能共同结束并返回建议。

关键战斗交互计划采用事件驱动模拟，即按事件发生的顺序计算各自效果。候选方案先通过快速评分缩小范围，再用详细模拟比较。局部战斗结果用于估计方案对整局目标的影响；只完成局部模拟时，返回结果注明评估范围。

### 任务执行、时间预算与结果返回

读取状态、检查输入等短操作采用请求后返回结果的方式。耗时的搜索和批量模拟作为可跟踪的任务执行：调用方取得任务标识，可以查询进度、取消任务并接收最终结果。具体用回调还是消息传递这些信息，随本地适配层一起确定。

建议入口为一次请求分配统一的计算截止时间，运营决策、战斗规划及其嵌套模拟共用这份预算。取消或超时信号向下传递；结束时优先返回已完成且通过合法性检查的候选，并注明搜索是否完成、评估范围和局限。尚无可用候选时，返回原因和需要补充的信息。

建议结果包含推荐操作、备选方案、适用状态与执行前提、推荐理由、预期收益和耗时估计，并说明依据来自规则检查、局部模拟还是整局模拟。有足够样本支持时再报告对应的统计值。未支持的机制、输入不足和计算失败分别记录，不能当作游戏失败计入通关统计。

玩家应用展示结果前核对请求标识和状态版本。玩家已更新局面时，将旧结果标为过期，并针对新状态重新请求。玩家仍在游戏中自行执行操作；核心根据反馈核对状态与动作前提，再更新记录。

策略评价使用玩家完成整局所花的总时间，包括操作、重试和等待工具计算的时间。总耗时按实际经过的时间统计，重叠发生的操作与计算只计一次；各部分耗时可另行记录用于分析。每次建议的计算预算结合整局剩余时间确定，研究端离线训练和批量实验另记耗时。

### 研究成果接入与评估记录

阵容研究器使用同一套环境和战斗评估接口开展批量搜索，输出候选阵容、适用条件及评估记录。供玩家端使用的候选和模型附带版本及规则适用范围：策略模块根据转换后的账号资源筛选配置、分配装备，环境检查是否合法；模型由建议入口检查输入输出及规则版本的兼容性，再交给策略模块使用。玩家每次请求建议时，直接使用已准备好的研究成果。

实验评估器驱动模拟对局或读取实际对局记录，收集状态变化、动作、事件、结果和耗时。模拟记录包含随机种子或随机源配置，实际对局记录保留观测内容及缺失信息。通过同一请求、候选和对局的标识，评估器可以追溯建议依据、复现模拟，并定位模拟与实测的差异；发现差异后交由规则或策略开发任务处理。

## 建议生成流程

面向玩家的一次建议请求，按以下顺序执行：

1. **建立请求。** 玩家应用提交账号资源、当前局面和整局时间预算。账号适配器整理资源，整局环境形成状态快照；关键输入缺失时，返回具体缺失项及其影响，供玩家补充。
2. **准备观测与预算。** 建议入口取得当前状态版本、可见信息和合法动作，根据已用时间及本次决策需要分配计算预算，并取得适用的阵容候选或模型。
3. **选择决策模块。** 商店、投资或阵容过渡等运营阶段由运营决策器生成方案；战斗准备、操作或重试阶段由战斗规划器生成方案。运营方案需要比较战斗收益时，按架构中的调用关系请求战斗评估。
4. **模拟并比较。** 候选方案先通过账号约束和动作合法性检查，再在独立状态副本上试算。环境调用战斗引擎处理战斗，在满足条件时完成节点结算；策略模块结合结果、后续局面和耗时比较方案，共用截止时间限制搜索范围。
5. **返回并展示。** 建议入口汇总推荐操作、备选方案、理由、预期收益及评估局限。玩家应用核对状态版本后展示；超时只返回已完成的可用结果，没有可用结果时展示原因。
6. **执行并更新。** 玩家在游戏中执行操作，将实际操作和结果反馈给应用。环境据此更新当前状态，重新检查旧建议，并在下一个决策点发起新请求。
7. **记录与复核。** 保存本次输入、版本、候选评估、推荐内容、实际操作、结果和耗时，供实验评估器回放比较。模拟与实测有差异时，保留对应记录以便复现和修正。

例如，在商店比较“购买角色”与“保留金币”时，运营决策器先生成两个合法候选，环境分别在副本上更新金币和阵容；需要比较接下来战斗的表现时，再调用战斗规划器。系统结合战斗评估、后续经济和所需时间给出建议。玩家确认实际购买后，当前局面的金币和阵容才按实际结果更新。

## 技术方案与选型依据

优先评估现有战斗引擎能否复用，Starclock 是待评估的候选之一。选型前记录候选引擎的具体提交版本、复现步骤、实际运行结果、已支持和缺失的机制，以及许可证。用选定的代表性战斗检查关键计算，再决定复用范围。

候选技术按用途划分如下：

| 用途 | 候选技术 | 原型需要检查的内容 |
| --- | --- | --- |
| 模拟与决策核心 | Rust | 规则能否正确实现、现有引擎能复用多少、单位时间能完成多少次模拟 |
| 研究与训练 | Python、PyTorch | 能否调用共用规则、开展批量实验并保存可复现的结果 |
| Windows 玩家应用 | TypeScript、Tauri | 录入与建议展示流程、与计算核心的连接、Windows 打包和资源占用 |
| 模型导出与玩家端接入 | ONNX | 研究模型能否导出和接入，以及 CPU 上的推理耗时和资源占用 |

各候选方案还需结合团队的开发经验和长期维护能力评估。通过对应阶段的小型原型后，记录采用的版本、选择理由和已知限制，再建立模块代码结构。

各模块开始开发前，共同确认本章架构中所需的接口字段和版本约定，并用同一组样例检查各端传入、返回数据的一致性。

## 运营模型与训练

### 候选模型

首轮采用稠密 Transformer 作为实验方案。角色、光锥、遗器、羁绊等实体分别编码，与当前可见局面、可用资源和任务条件共同输入共享网络；站位、装备归属等关系显式表示。策略头对合法操作评分，价值头估计在当前任务条件与后续策略下成功的可能性。训练与推理使用一致的观测和动作编码。

先比较约 500 万、2000 万和 5000 万参数的模型，参数量指共享编码器、策略头与价值头的总量。上述规模是实验范围，最终结构和参数量在原型中统计。比较相同模拟对局数量与相同训练时间下的结果，并固定推理和搜索预算，检查效果、CPU 耗时及资源占用。根据结果确定是否扩大模型或试验混合专家等结构。

训练程序通过整局环境调用共用规则，显式传入随机源。策略输入包含当时可见的信息与已确认资源；完整隐藏状态、未来发牌和随机种子用于环境计算及回放。战斗结果需要反映胜负、损血、资源变化和耗时，支持模型学习保血、补强和长期经济之间的取舍。

### 从零探索与训练阶段

首轮从随机策略开始强化学习，PPO 是待验证的算法候选。模型自行产生对局经验；模仿学习可用于后续学习已经验证的搜索结果或优秀轨迹。搜索得到的动作和旧轨迹用于单独的学习步骤，PPO 更新使用按对应策略采集的数据。

训练按以下目标逐步扩展，各阶段持续混合已经学过的任务：

| 阶段 | 主要练习内容 | 评估重点 |
| --- | --- | --- |
| 基础运营 | 在较短流程中探索买卖、升级、刷新、投资和阵容调整 | 与随机及简单规则策略比较，检查跨节点决策收益 |
| 完整对局 | 从开局推进到结算，练习过渡、资源分配和转阵 | 独立发牌与敌人场景中的通关结果 |
| 多种打法 | 随机或指定核心角色、羁绊和装备条件，自行寻找搭配 | 各类打法的成绩、较弱方向与未见组合的适应能力 |
| 全试用 SSS | 使用真实试用配置，针对最终血量 ≥100 练习保血和困难节点 | 分打法统计 SSS 率、最终血量及失败原因 |
| 连续挑战 | 从连续 3、5 局逐步增加到 20 局，加入重开限制和打法差异条件 | 整套挑战完成率、失败位置、已用打法与剩余选择 |

不同账号和打法从早期加入，后续扩大覆盖范围。起步配置保留一定余量，并持续混合高、中、低配置；按训练表现调整采样，增加模型已有进展但仍不稳定的任务。各类配置分别评估，保留固定测试集。全试用作为持续练习的任务，第四阶段重点优化其 SSS 表现。每次训练明确成功条件；辅助奖励的效果通过实验核对。

### 优秀打法与连续挑战

模型负责根据局面决策，优秀打法档案保存已探索出的阵容、账号条件、过渡路线、装备分配、操作轨迹和多次测试结果。模型探索产生候选，独立评估后进入档案；训练程序从不同类别抽取练习，帮助模型持续掌握多种打法。

打法差异按[挑战目标](project-overview.md)约定的最高伤害角色或决定性因素判断。档案同时保留核心羁绊、投资、装备和关键辅助等机制信息。决定性因素可以通过合法的替换方案开展对照模拟，记录对胜率和保血的影响；分类与对照方法在评估前固定。MAP-Elites 是维护多类优秀候选的可选方法。

连续挑战的观测增加已完成局数、已使用打法和剩余任务条件。可以先通过档案和搜索安排候选，再评估是否需要独立的挑战规划模型。当前挑战中的 SSS 按最终血量 ≥100 判断；当前血量与上限分别输入，整局重开和战斗重试按任务设置限制。

## 策略研究与评估

研究阶段可以比较以下方法的效果和成本，再决定各自适用的任务：

- MAP-Elites：按策略特征分组，在各组中保留表现较好的候选，探索不同类型的阵容和打法。
- Beam Search（束搜索）：每轮只保留一定数量的候选方案，继续搜索后续操作。
- MCTS（蒙特卡洛树搜索）：采样可能的后续过程，估计不同操作的收益。
- 模仿学习：从已有决策样本中学习如何选择操作。
- 强化学习：根据与环境交互得到的反馈学习策略。

每次实验至少记录代码版本、规则版本、账号配置、场景、模拟随机种子、策略参数、结果和耗时。比较策略时使用一致的账号资源、场景和时间预算，并设置参照策略。

样本按账号配置及整局分组，确保同一局留在同一组，连续挑战记录也按完整挑战分组。完成搜索与调参后，用未参与训练或调参的账号、场景及组合检查效果；映射到同一生效配置的来源数据按同组处理。

模拟与真实对局分别报告通关率、SSS 率、整套挑战完成率、样本量和耗时，并按账号资源和打法分类，检查表现较弱的方向。失败案例及模拟与实测的差异保留记录，用于后续修正规则和策略。模型导出时附带数据快照、规则版本、输入输出约定和适用任务；版本兼容性由建议入口检查。

任务指定时间预算时，同时报告预算内达标率：在预算内完成且满足成功条件的有效样本数，除以全部有效评估样本数。超时样本保留在分母中，最终对局结果另记；计算异常和输入缺失按前述异常分类报告。
