# 系统设计与技术方案

状态：讨论稿。日期：2026-11-05。

## 模块职责

系统计划围绕完整对局搭建，让运营决策与战斗规划共用状态、规则和评估数据。

| 模块 | 职责 | 产出 |
| --- | --- | --- |
| 战斗引擎 | 计算伤害、行动顺序、技能、状态和事件触发 | 战斗结果与事件记录 |
| 整局环境 | 推进节点，处理商店、投资、经济和生命结算 | 更新后的状态、当前可见信息、合法操作 |
| 战斗规划器 | 比较操作序列、站位、自动策略及重试时机 | 在给定时间内生成的战术建议 |
| 运营决策器 | 决定购买、升级、储蓄、投资、阵容过渡及转型 | 当前节点的运营操作 |
| 阵容研究器 | 探索角色、装备和羁绊之间的配合 | 候选阵容及适用条件 |
| 账号适配器 | 根据账号资源安排可行配置和装备分配 | 符合账号资源条件的候选方案 |
| 实验评估器 | 回放对局、比较策略、记录模拟与实测的差异 | 可复现的实验报告 |
| 玩家应用 | 输入局面、展示建议、记录结果 | 可在 Windows 本地完成的使用流程 |

关键交互采用事件驱动模拟，即按事件发生的顺序精确计算其效果。先用快速评分初筛候选策略，再通过详细模拟和真实对局样本逐步验证。

## 技术方案

优先评估现有战斗引擎能否复用，Starclock 是候选之一。下一阶段先整理[本地审计材料](../.audit/)中可复现的证据，再检查候选引擎的具体提交版本、运行结果、已支持的机制和许可，确定选型。

候选技术方案为：用 Rust 实现模拟与决策核心，用 Python 开展研究和训练，用 TypeScript 开发桌面界面。Tauri、PyTorch、ONNX 等组件在对应阶段通过小型原型验证，再记录选型结果。

选择技术方案时，考虑团队能否长期维护、现有引擎有多少代码可以复用、单位时间能完成多少次模拟、CPU 推理的耗时和资源占用，以及 Windows 打包是否方便。各模块开始开发时建立代码结构。共用的游戏规则统一实现，训练端与应用端通过接口调用。

## 策略研究与评估

研究任务可尝试以下方法，并通过与参照策略比较决定如何采用：

- MAP-Elites：按策略特征保留多类优秀候选。
- Beam Search（束搜索）：每轮保留有限数量的候选继续搜索。
- MCTS（蒙特卡洛树搜索）：通过采样评估后续操作。
- 模仿学习：学习已有决策样本。
- 强化学习：根据环境反馈学习策略。

每次实验至少记录代码版本、规则版本、账号配置、场景、随机种子、策略参数、结果和耗时。策略比较采用一致的评估条件；完成搜索与调参后，用独立场景检查效果。分别报告模拟通关率和真实对局通关率，并附各自的样本量。
