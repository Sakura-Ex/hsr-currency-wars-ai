# 文档写作规范

## 写作原则

- 面向读者的实际任务组织内容，让读者能找到信息、完成操作并判断结果。
- 保持准确、清楚、直接。用具体动作、对象和结果说明问题。
- 命令、路径、配置和示例与当前项目保持一致。
- 说明必要的前提、限制和重要设计决定。
- 不重复维护同一内容；相关文档通过链接关联。

## 语言风格

- 说明文档使用中文，代码标识符、路径及工具固定字段保留原名。
- 使用简洁、自然、具体的表达，一句话尽量只讲一个重点。
- 优先正向陈述，直接说明是什么、怎么做、会得到什么结果。
- 少用抽象词、空话、套话和不必要的术语。
- 使用自然易懂的表达，避免生硬的名词组合。
- 术语前后一致；读者可能不熟悉的术语首次出现时作简要解释。
- 操作步骤明确写出动作和预期结果。

## 文档组织

- 将 `docs` 视为一份完整文档，各文件按章节分工，标题应让读者一眼看出内容。
- `docs/README.md` 按章节顺序列出标题和链接。
- 根据已有内容划分章节，内容增长后再拆分。
- 操作步骤按执行顺序编号，其他并列内容使用项目符号。
- 长章节先列出提纲，再按主题分组。

根目录 `README.md` 介绍项目、当前进展和运行入口，并链接文档目录。`AGENTS.md` 记录代码助手的操作约定；`CONTRIBUTING.md` 提供贡献入口，并链接相关章节。发布时用 `CHANGELOG.md` 记录用户能感知的变化。

## 文档维护

- 新增章节时，在 `docs/README.md` 中添加标题和链接。
- 功能、配置或流程变化时，同步更新相关文档。
- 删除功能时删除相关说明，更换方案时更新正文和链接。
- 在正文中区分规划、已实现的行为和实测结果。
- 变更过程及原因保存在 Git、Issue 和 PR 中。
- 修正过时内容，保持各文档之间一致。
- 让读者能够根据说明完成目标，并判断操作是否成功。

## AI 写作注意事项

- 正面说明要求或结果，避免补充无必要的否定或免责说明。
- 不在文档中说明内容来源。
- 新增规则的篇幅和语气应与已有规则一致。
