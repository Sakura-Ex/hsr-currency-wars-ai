# 实施计划与人员分工

状态：讨论稿。日期：2026-11-05。

## 实施与验收

每个阶段先选定用于验收的具体场景，再开始开发。

| 阶段 | 工作内容 | 验收条件 |
| --- | --- | --- |
| M0：协作准备与技术选型 | 建立贡献规范；整理引擎审查材料；选定代表性战斗；确定首个样例需要表示的状态和记录的字段 | 三人能按同一份说明复现样例；选择引擎的依据明确且可验证 |
| M1：跑通最小战斗与节点流程 | 实现选定角色、敌人和机制，串联战斗及节点经济结算 | 固定输入和随机种子后，结果可复现；关键数值与已记录样本吻合 |
| M2：搜索战斗方案 | 建立用于比较的参照策略，在限定范围内搜索操作或站位方案 | 在同一批样本上报告收益、耗时及失败案例；结果可回放 |
| M3：运行完整对局与研究阵容 | 补齐选定版本的整局流程，探索阵容及过渡路线 | 能完整运行对局；候选策略在独立评估场景中与参照策略比较 |
| M4：学习运营策略与适配账号 | 在已验证的环境中学习运营策略，接入账号样本 | 对不同账号分别报告通关结果、样本量与耗时 |
| M5：玩家预览版 | 打包本地建议工具，集成录入、展示及记录功能 | 普通 Windows 设备可完成一次实际使用流程，并记录资源占用 |

## 三人首轮分工

| 负责人 | 首轮工作 | 交付内容 |
| --- | --- | --- |
| 项目发起人 | 确定场景与规则，安排实际游戏测试，维护目标与验收标准 | 代表性战斗、观测记录、M1 验收清单 |
| 伙伴 A | 整理引擎审查材料，验证战斗计算，提出复用方案 | 可运行样例、关键机制的模拟与实测对比、引擎选择及理由 |
| 伙伴 B | 建立整局状态与回放记录，配置代码格式和测试检查 | 样例数据、最小节点流程、首批持续集成（CI）检查 |

具体负责人按技能调整。每项任务安排一人负责、一人评审；共同确认模块之间传递的数据字段后，再分头实现。开始设计玩家使用流程时，同步开发界面。

## 第一轮实施顺序

1. 根据[项目目标与使用方式](project-overview.md)和本章计划，确认共同目标、第一轮使用的样例和三人的职责。
2. 将长期开发原则写入 `AGENTS.md`，在 `CONTRIBUTING.md` 中链接[开发与测试约定](development-guide.md)和[Git 协作规范](git-workflow.md)，更新根 `README.md` 的文档入口和语言声明。
3. 添加简洁的 Issue 和 PR 模板，使用[Git 协作规范](git-workflow.md)中的任务和 PR 字段。
4. 整理审查已有引擎时收集的证据，运行代表性样例，确定首先开发的模块和使用的工具链。
5. 为已采用的工具链配置格式检查、核心测试和 Windows CI。
6. 在 GitHub 配置主分支评审及检查要求，用第一个小 PR 验证完整协作流程。

第一轮完成后，新伙伴应能复现样例、提交改动并完成评审。此后每周检查一个可运行的成果，根据实测结果调整下一轮任务。
