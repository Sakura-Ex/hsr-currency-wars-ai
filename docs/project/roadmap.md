# 实施阶段与任务拆解

状态：讨论稿。日期：2026-11-10。下列开发与训练任务均待实现。

任务按 M0—M5 推进，编号用于关联 Issue、PR 和依赖项。模块接口见[系统设计与技术方案](architecture.md)。

每阶段先确定版本、支持范围、验收样本及预期结果。策略比较使用明确的参照策略、账号、样本量和整局时间预算，评价目标见[项目目标与使用方式](overview.md)。

## 当前先做：账号与遗器数据

先落实 M0.4 和 M1.1 的账号部分，交付范围为一个角色、一个光锥与六件遗器。数据表示和生成要求见[账号与遗器数据](../modules/account-generation/design.md)。

| 交付物 | 完成判断 |
| --- | --- |
| 原始配置及字段说明 | 角色、光锥、星魂、行迹和遗器实例均有明确 ID、单位与等级口径，来源及装备关系可追溯 |
| 遗器规则数据与生成样例 | 注明规则依据和验证状态；固定种子可复现，主副词条、强化过程和结果可核对 |
| 配置转换输入输出 | 用练度不足映射与试用样例核对生效等级、行迹、属性和机制引用，供模型及战斗侧共用 |
| 账号资源指标 | 固定金数和遗器词条的统计口径，给出资源集中与分散的样例；生成目标与实际指标可比较 |

数据与模型负责人先整理账号样例、遗器生成规则及模型输入需求。运营模拟负责人维护局面、经济、商店、可用资源与合法操作；战斗模拟负责人维护战斗状态、机制及战斗结果。配置转换的实现归属由三人对接时明确，其规则和输出共用。

三人共同核对一条流程：原始账号配置转换为生效配置，运营侧在该资源约束下执行一次操作，组装战斗输入，战斗结束后由运营侧结算血量和资源。账号数据任务先验证配置与生成结果；运营侧使用已核对的战斗结果样例验证战后结算，战斗侧使用独立输入核对数值和事件顺序。两个最小样例完成后，使用真实战斗引擎贯通并核对一个节点。完整对局训练依赖已验证的环境。

除请求和状态版本等通用标识外，首个节点的交接样例需要共同约定：

| 交接内容 | 需要约定的信息 |
| --- | --- |
| 共用资料 | 数据快照、条目类别与 ID，以及角色形态、星级和站位的表示方式 |
| 战斗输入 | 双方配置、节点与难度、影响战斗的投资和环境效果、随机种子或状态，以及战斗操作 |
| 战斗结束结果 | 胜负、战斗内用时、结算所需统计，以及按规则需要保留的状态 |

重试与重新进入时的随机状态处理按已验证规则确定，沿用系统设计中的结算时机和状态维护职责。

## 任务对接与交付

- 任务写明编号、依赖、输入输出样例和验收方法。接口明确后可并行开发，接入实际模块后记录联调结果。
- 交付分支与提交版本、样本、运行命令、实际结果和剩余问题；PR 中关联未合并的依赖。
- 通过任务分支和 PR 对接改动，遵循主分支保护要求；具体流程见[Git 协作规范](../development/git-workflow.md)，验证要求见[开发与测试约定](../development/development-guide.md)。

模拟和真实对局分别报告结果、样本量与局限。玩家整局耗时包括操作、重试和等待计算，重叠时间只计一次；研究端耗时另记。

## 拿到任务后怎样开始

任务表用来查看整体范围。实际开始时，把选中的一项展开成“解决的问题、已有输入、操作步骤、交付物、完成判断”。当前账号任务使用本章开头的交付表和[首个账号样例](../modules/account-generation/design.md#首个样例与完成条件)；下面以 M0.1、M0.2 和 M2.2 说明战斗侧与候选生成任务。

账号数据可从 M0.4 的最小配置开始；战斗侧从 M0.1 选择样例，再用 M0.2 整理观测记录；运营侧选一个商店操作和节点结算样例。候选引擎验证使用战斗样例，各端代码使用对应的接口和输入。缺少依赖时列出具体缺项，并准备输入输出草稿，接口确认后继续实现。

### M0.1 示例：确定第一场要核对的战斗

**要解决的问题：** 明确第一轮模拟要覆盖什么。完成后，下一项任务应能据此收集材料，并知道需要检查哪些现象。

**先准备：** 一场能够再次进入或已有完整记录的战斗，以及可取得的版本、节点、双方配置和操作方式。可以先用现有截图、录像或手写记录；暂时缺少的信息列为待补充。

**具体操作：**

1. 选一场配置和过程便于记录的战斗，写清怎样进入、使用什么阵容及装备、采用自动还是手动操作。
2. 从中选一个可观察的问题作为首个核对目标，例如“开战后最先行动的单位及顺序”。说明需要哪些配置与画面记录才能核对它。
3. 列出本次覆盖的过程和机制、已有材料、缺失材料，以及需要记录的结果项。已有观测时注明依据，尚未采集的内容标为“待记录”。

**AI 可以协助：** 把已有材料整理成说明，找出缺失信息，检查任务范围是否过大，生成下一步的记录表。版本、配置和战斗结果以实际记录为准，AI 将无法确定的内容标为待补充。

**交付物：** 在任务 Issue 中填写以下样例说明，作为 M0.2 和 M0.3 的共同输入。引用的材料应适合该 Issue 的可见范围，并能由后续任务访问。

```text
样例编号：
游戏版本与节点：
进入方式：
双方已知配置：
自动或手动操作方式：
本次核对的问题与范围：
已有材料及引用：
待补充内容：
预期结果及其依据，或待记录项：
```

**完成判断：** 阅读这份说明后，能够知道要记录哪场战斗、关注哪段过程、还需补什么材料。M0.1 完成表示样例已选清楚；M0.2 继续补齐观测记录。

### M0.2 示例：把战斗过程整理成可核对的记录

**要解决的问题：** 为之后的模拟提供明确输入和可比较的观测结果。

从 M0.1 的样例说明开始，先记录进入战斗时的可见配置，再按时间顺序整理选定片段中的操作与事件。每条记录写明序号或录像时间、操作、操作前后的可见状态，以及截图或录像位置。自动战斗也记录观察到的事件；看不清的数值标为未知。

AI 可以帮助整理表格、检查前后记录是否矛盾、列出缺失项。整理后逐项回看原始材料，核对单位、数值和顺序。观测到的事实与对规则的解释分开记录。

**交付与完成判断：** 交付初始状态、操作与事件记录、材料引用和缺失项清单。选定核对目标所需的输入与观测齐全后，交给 M0.3 验证引擎及 M1.4 比较模拟结果；关键材料尚缺时，注明该目标仍待补齐。

### M2.2 示例：让 AI 帮助生成合法候选

**要解决的问题：** 给定一个局面，列出当前允许尝试的方案，供 M2.3 评分和搜索。

**开始条件：** 已有 M1.1 的观测、账号约束和合法动作接口，以及可运行的输入样例。先选择接口已经支持的一类操作作为范围，例如允许的站位调整。

可以将下面的要求交给 AI：

> 本次只做 M2.2。先找到现有观测、资源约束和合法动作接口，以及对应的输入样例，列出实际路径和字段。若依赖尚未实现，列出缺项并给出接口草稿。依赖齐全后，针对选定的一类操作生成候选，每项包含候选标识、来源状态版本、操作参数和前提条件。使用现有规则检查候选，保持输入状态不变。给出运行方法，展示正常输入、受约束输入和无可用动作时的结果。候选质量由 M2.3 继续评价。

**交付物：** 候选生成代码、输入输出样例、运行命令与实际检查结果。每个候选应能由下游按既定接口读取；没有候选时返回可识别的结果及原因。

**完成判断：** 对选定的小样例，结果与事先核对的合法候选一致，资源不足或阶段不允许的操作被排除，原始状态未被修改。将通过检查的候选列表交给 M2.3。
